## Частина I. Специфікація ЛР1

### Діалог 1. Неоднозначності вимог

**Користувач:** Потрібен розбір саме Luden, не Issue Tracker. Знайди суттєві неоднозначності: для кожної — фрагмент джерела або відсутнє правило, ризик і позначку «факт / відкрите / припущення». Уже закриті рішення винеси окремо.

**Розробник:** Найбільші прогалини — життєвий цикл замовлення, повторна покупка й кількість копій, суміщення Admin і покупця, сесія після реєстрації, правила пароля. Уже задані: публічний каталог, бібліотека лише після входу, відкладення бонусів.

**Користувач:** Не приймай відповіді AI за рішення замовника. Звір з Decision Log і Product Baseline.

**Розробник:** Звірено з Q-06–Q-11 і SRC-01–SRC-06. Пропозиції моделі залишено як кандидати, не як затверджені BR.

### Діалог 2. Пріоритети для контракту

**Користувач:** Які три відкриті рішення найбільше блокують формальний контракт ЛР1 і майбутні тести?

**Розробник:** Q-07 (матриця станів) блокує сценарії оплати й бібліотеки; Q-06 — кошик і повторну покупку; Q-08 — матрицю прав. Для кожного є варіанти на погодження, жоден не позначено ухваленим. Без відповідей замовника вже можна формалізувати реєстрацію/вхід, публічне читання каталогу й доступ до власної бібліотеки після Paid/Completed.

**Користувач:** Добре. У контракт переносимо лише підтверджене; інше лишається питанням.

### Діалог 3. Чернетка моделі й правил

**Користувач:** Склади чернетку того, що вже можна формалізувати: дані, замовлення, кошик, бібліотека, помилки. Відокрем факти від технічних рішень команди й від Q-06–Q-11. Поля MIT не переносити.

**Розробник:** Джерела вже задають реєстрацію/вхід, каталог, склад і суму кошика, валюту на оформленні, доступ до ігор лише з власних Paid/Completed. Повна схема полів, кількість копій і повна матриця переходів ще не закриті джерелом.

**Користувач:** Це перелік для формалізації, не готова схема БД. Q залишаються відкритими.

### Діалог 4. Приховані припущення

**Користувач:** Покажи п’ять тверджень, які виглядають як вимоги, але джерело їх дослівно не дає. Як чесно позначити в requirements.md?

**Розробник:** Окремо позначено технічні рішення про підтвердження пароля, жанри, структуру кошика, знімок ціни. Кількість копій — Q-06. Форму відповіді на чужі дані не виводимо «автоматично» з BR-03 без явного правила.

**Користувач:** Факт і припущення розділяємо. Схему помилок цим діалогом не затверджуємо.

### Діалог 5–6. Рев’ю ПЗ1–2 і AC

**Користувач:** Перевір узгодженість історій і AC, Figma vs майбутній сервіс, повноту API й тестів. Не вигадуй дефектів заради звіту.

**Розробник:** Підтверджено відому розбіжність маршруту після покупки у Figma з очікуваним доступом до гри. Інших доведених текстових суперечностей немає. Для сервісу бракує єдиного контракту даних, API й простежуваності до тестів.

**Користувач:** Дефект Figma вже в журналі — відсунь. Дай три прогалини саме специфікації сервісу й одну перевірювану редакцію слабкого AC без вигаданих чисел і без закриття Q.

**Розробник:** Пріоритети: контракт даних і станів; API заявлених дій; точні майбутні тести. Для AC-03.4 запропоновано: після успішного повторного завантаження помилка зникає, картки відповідають списку. Це пропозиція команди, не прийнятий критерій.

### Діалог 7. Документаційний пакет ЛР1

**Користувач:** Зроби всі правки за планом: реальні сутності User/Product/Bill/BillItem, відокремлення чинного API від target, матриця, AC, BR, тести, походження.

**Розробник:** Прийнято як редакцію документації. Відхилено застарілі твердження («сервісу немає», UUID/price_minor як факт коду, вигадані шляхи /games/orders). Перевірка — статичне читання ланцюжків і validation.md; продуктові тести не запускались.

### Діалог 8. UX-джерела й семантика AC

**Користувач:** Дороби виправлення за новим планом. Усі четверо учасників провели колективне перехресне review.

**Розробник:** Порівняно AC з історичними Input Pack; відновлено password-toggle / cancel / навігацію й порядок AC-06.3/06.4; зайве винесено в EXT/BR. Оригінальний сенс AC має пріоритет над реконструкцією; profile destination не підміняється library без погодження. Артефакт — фінальна docs-редакція ЛР1 за VERSION.txt.

**Користувач:** Тема Luden узгоджена усно з викладачем до `lab02-skill-v0`. У звіті так і напиши: листа в репо немає, підтвердження — на занятті.

**Розробник:** Зафіксовано в `docs/lab-02.md` і acceptance-map.

### Діалог 10. Крок 0 — коли вмикати Skill

### Діалог 11. AI-draft зрізу B

**Користувач:** Під Skill реалізуй PATCH `/api/bills/{id}/status` і сценарії T09/T10. Контекст — лише дозволені файли зрізу B.

**Розробник (AI-чернетка):** Додано `ALLOWED_TRANSITIONS`, 409 без UPDATE на заборонений перехід, повтор того самого статусу → 200. З’явилась пропозиція `bill_events` і правки `database.py`.

**Користувач:** `bill_events` і зайву схему відхиляємо. `sales_count` лише на Processing→Paid. Перевір власника Bill.

**Розробник:** Відхилено `bill_events` і зміни схеми БД. Залишено матрицю й коди 200/409; додано ручні правки sales_count і ownership. Diff збережено в `patches/lab02-ai-draft-slice-b.patch`. Тег `lab02-ai-draft`.

### Діалог 12. Skill v0 → v1

**Розробник:** У `references/slices.md` для зрізу B заборонено чіпати `database.py`; додано примітку про відхилення `bill_events` (Skill v1).

### Діалог 13. Мікроексперимент (пілот і співмірний повтор)

**Користувач:** Потрібен мікроексперимент AI / no-AI за методичкою.

**Розробник:** Спочатку пілот: `matches_query` (no-AI) і `matches_category` (AI). Час і результати записано, але принцип різний (підрядок vs exact) — для висновків про перевагу AI не годиться.

**Користувач:** Не переписуй пілотні хвилини. Зроби співмірну пару з однаковим принципом і чесними обмеженнями.

**Розробник:** Додано `equals_ci` (no-AI) і `role_equals_ci` (AI) — exact equality ignore case; жереб до коду; протокол у `experiments/protocol.md`. Пілот позначено `pilot-dissimilar-predicates`. Обмеження: один виконавець, sequential-same-session. Висновок «AI кращий» не робимо.

### Діалог 14. Повне покриття зрізів A–D і evidence

**Користувач:** Добери каталог, Bill items, бібліотеку, фільтри, ізоляцію БД від `data/app.db`. `init_db` не повинен створювати файл на імпорті модуля.

**Розробник:** Реалізовано маршрути Product/Bill/library, фільтри `q`∧`category`, T01–T14, `tmp_path` у conftest, lifespan-only `init_db`. Тег `lab02-implemented`.

### Діалог 15. Рев’ю доступу: профіль, бібліотека, repurchase

**Користувач:** За BR-03 профіль і бібліотека — лише власник. Admin не читає чужу бібліотеку. За BR-05 Paid/Completed не можна купувати знову; Declined не блокує. Додай тести.

**Розробник:**  
- `GET /api/users/{id}` — лише `X-User-Id` власника; чужий/Admin→не свій → 403; немає → 404.  
- `get_library` — без Admin-override.  
- `create_bill` — 409, якщо Product уже в Paid/Completed.  
Тести: `test_users.py`, оновлені library/bills.

**Користувач:** Skill має явно знати, куди класти профіль.

**Розробник:** Додано зріз **E** у `slices.md` (обидві копії Skill), критерії BR-03 / SRC-06, файл `tests/test_users.py`.
